# XM²code 本地安全基线设计

日期：2026-08-24
状态：用户已批准方向，等待书面规格复核

## 1. 目标与范围

本阶段把 XM²code 变成可以交给真实初学者进行封闭测试的本地桌面版本。安全目标不是阻止玩家查看离线安装包，而是确保任何玩家代码、课程内容、导入存档或页面行为都不能获得宿主电脑权限，且异常运行不会冻结游戏或破坏存档。

本阶段包含：

- 删除 Electron 主进程调用系统 Python 的能力；
- 删除 JavaScript `new Function` Python 模拟器；
- 暂时移除 AI 助手、DeepSeek 请求和本地 API Key 存储；
- 建立可终止、可重建、默认无网络和无宿主文件权限的 Python Worker 边界；
- 加固 Electron 窗口、导航、权限和 IPC；
- 为存档增加版本、校验、备份和失败恢复；
- 增加针对恶意代码、恶意消息、恶意存档和桌面权限的回归测试。

本阶段不包含登录、云同步、AI 代码翻译、服务器执行代码、应用商店签名、公网服务或完整 104 关内容重写。

## 2. 方案比较

### 方案一：继续修补 JavaScript Python 模拟器

优点是改动较少、包体积小。缺点是它依赖动态 JavaScript 执行，语义会持续偏离真实 Python，随着课程深入还要不断模拟标准库。它既不能成为可信教学环境，也会妨碍严格 CSP，因此不采用。

### 方案二：继续调用系统 Python，并依赖操作系统权限

优点是 Python 语义真实。缺点是不同平台配置不同，玩家必须安装 Python，而且当前 Electron 应用无法仅靠超时阻止文件、网络、进程和环境变量访问。要安全使用需要平台级容器或虚拟机，成本和维护复杂度不适合第一版，因此不采用。

### 方案三：使用 WebAssembly Python Worker

普通课程使用随应用交付的 Pyodide 运行时，在独立 Web Worker 中执行。主页面只通过固定消息协议发送代码和输入；超时后终止整个 Worker。运行时只接触临时虚拟文件系统，不获得 Node、Electron 主进程或宿主文件权限。这是本阶段采用的方案。

Worker 不是单独的安全结论。只有同时完成 Electron 隔离、消息校验、资源限制、依赖固定和攻击测试，方案才算通过。

## 3. 架构边界

### 3.1 Electron 主进程

主进程只负责创建窗口和应用生命周期，不接收、保存或执行玩家代码。必须删除 `child_process`、临时 `.py` 文件以及 `run-python` IPC。

窗口保持 `contextIsolation: true`、`nodeIntegration: false`，并增加 `sandbox: true`。默认拒绝权限申请，禁止渲染页面任意导航、新窗口和非白名单外部协议。正式构建只加载随应用打包的本地页面。

### 3.2 Preload

Preload 仅暴露游戏确实需要的最小信息。第一阶段只保留冻结后的平台枚举值，不暴露通用 IPC、文件、shell、网络或代码执行方法。所有将来新增的桥接方法都必须有固定通道名、参数类型、长度上限和返回结构。

### 3.3 课程页面

课程页面依赖统一的运行接口，不知道 Pyodide 的内部实现：

```ts
runPython({ code, input, timeoutMs }): Promise<RunResult>
stopRun(): void
```

页面一次只允许一个运行任务。重复运行先终止旧任务并创建新 Worker。页面卸载时必须终止 Worker，避免后台继续耗费资源。

### 3.4 Python Worker

Worker 接受带版本号和运行 ID 的消息。每次运行使用全新的 Python 全局命名空间和临时虚拟文件系统。第一版只允许课程白名单中的内置模块，不允许玩家触发任意包下载。模块白名单用于保证教学范围，不能被当作安全沙箱；即使玩家尝试通过 `js`、`pyodide` 或导入机制接触 Worker 全局对象，外部网络和宿主能力仍必须在 Electron 与 Worker 边界被阻断。

运行控制包括：

- 默认 5 秒超时；
- 代码和输入各自的长度上限；
- 标准输出和错误输出的总长度上限；
- 虚拟文件数量及单文件大小上限；
- 超时、停止、Worker 崩溃后终止并重建；
- 返回结果仅包含固定字段，不返回运行时对象。

Worker 包装器使用仅存在于 JavaScript 闭包中的一次性能力标记识别合法结果，页面拒绝玩家 Python 通过 `postMessage` 伪造的完成消息。外部 `http`、`https`、`ws` 和 `wss` 请求由 Electron 会话层默认拒绝，不能只依赖 Python 导入黑名单。

浏览器 Worker 无法可靠实施硬内存上限，因此内存炸弹的安全策略是：限制输入和课程可用模块、设置输出上限、在独立 Worker 中运行，并在 Worker 失联时终止。若测试证明某平台仍可拖垮主界面，该平台不得进入封闭测试。

## 4. 依赖交付

Pyodide 及其标准库文件随桌面应用打包，不在玩家运行代码时访问 CDN。运行时版本写死并进入锁文件，构建阶段校验静态资源清单和哈希。第一版不提供 `micropip` 和任意 URL 安装入口。

内容安全策略默认禁止 `unsafe-eval`。如当前 Chromium 运行 WebAssembly 需要 CSP 授权，只允许更窄的 `wasm-unsafe-eval`，不能因此开放普通字符串求值。`connect-src` 默认关闭外部网络，Worker 和运行时资源只从随包的受信本地来源加载。因此旧 `new Function` 模拟器必须在启用严格 CSP 前彻底移除，不能保留为隐藏备用路径。

## 5. AI 功能退出规则

第一版不是隐藏 AI 按钮，而是删除：

- `AIChat` 在课程页面的引用和渲染；
- DeepSeek API 地址和请求代码；
- 设置页中的 DeepSeek API Key 输入；
- `localStorage` 中的 API Key 读写方法；
- 与 AI 请求相关的网络许可。

升级时只删除该配置键，不读取、导出或上传旧值。以后重新加入 AI 时，必须单独设计服务端密钥、玩家同意、代码脱敏、费用限制和未成年人隐私规则。

## 6. 存档可靠性

存档接口与底层存储分离。UI 继续表现为一个默认存档槽和“添加存档槽”按钮；底层存档包包含：

- `schemaVersion`；
- 存档 ID、创建时间和更新时间；
- 课程版本、进度、草稿、复习记录和设置；
- 对规范化数据计算的完整性校验值。

每次升级先复制旧存档到独立恢复记录，再执行纯函数迁移。迁移成功并通过校验后才替换活动存档；失败时保留旧存档并显示可理解的恢复提示。导入文件必须限制大小、JSON 深度、字段集合和版本，不允许导入内容决定文件路径、模块名或可执行代码。

第一阶段可以继续以 `localStorage` 作为物理介质，但只能通过新的存档仓库访问，并保留最近三份有效恢复记录。后续迁移 SQLite 时保持仓库接口不变。

## 7. 离线判题边界

离线安装包中的测试和参考答案无法对有意反编译的玩家保密，因此产品不宣称隐藏测试不可提取。

普通学习体验仍应：

- 不把参考答案放进课程页面状态；
- 使用不同数据生成变体测试；
- 只对学习目标进行 AST 结构检查；
- 避免在失败消息中显示完整测试答案；
- 使用独立项目和延迟复习验证迁移能力。

判题器不得执行主运行器没有执行过的玩家代码，也不得拥有额外系统权限。

## 8. 错误处理

所有运行结果归一为：`passed`、`runtime_error`、`timeout`、`stopped`、`output_limit`、`worker_crash` 或 `invalid_request`。无论出现哪一种状态，运行按钮都必须恢复可用；需要重建 Worker 的状态不得继续复用旧实例。

安全错误向玩家使用大白话解释，但开发日志只记录错误类型、课程 ID 和运行 ID，不记录完整玩家代码、输入、API Key、用户路径或个人信息。

存档损坏时不自动覆盖。界面显示最后一个有效恢复点，并让玩家选择恢复或导出损坏副本用于人工排查。

## 9. 测试与发布门槛

### 9.1 单元与集成测试

- IPC 源码契约：项目中不存在 `run-python`、`execFile('python3')` 或玩家代码 IPC；
- CSP 契约：正式页面不允许 `unsafe-eval`，源码中不存在 `new Function`；
- AI 退出契约：课程、设置和存储中不存在 DeepSeek 入口；
- Worker 协议：拒绝缺字段、未知字段、超长代码、超长输入和过期运行 ID；
- 生命周期：超时、停止、崩溃和页面卸载都会终止 Worker；
- 输出限制：超大输出返回 `output_limit`，界面不冻结；
- 存档：正常保存、损坏校验、迁移成功、迁移失败回滚、恶意导入均有测试；
- Electron：导航、新窗口、权限请求和非白名单协议均被拒绝。

### 9.2 攻击样例

测试必须覆盖无限循环、无限递归、超大输出、超大列表、宿主文件读取、网络请求、子进程、路径穿越、恶意 Worker 消息、伪造存档以及渲染进程调用未授权桥接方法。

至少对一项关键安全测试执行变异验证：暂时移除对应防护，确认测试会失败，再恢复防护并确认测试通过。

### 9.3 封闭测试准入

只有同时满足以下条件才能交给 10 名初学者：

1. 完整单元测试、课程校验和生产构建通过；
2. 攻击样例不会获得宿主权限或冻结主界面；
3. Electron 源码契约和运行时权限检查通过；
4. 存档迁移失败可以恢复；
5. 安装包不包含系统 Python 执行和 AI 密钥代码；
6. 已知限制写入测试说明。

这次封闭测试只验证安全性、可用性和教学方向，不用于宣称玩家已经从零基础达到入门开发者。

## 10. 实施顺序

1. 先用源码契约测试锁住必须删除的高风险能力；
2. 删除 AI 和系统 Python 通道并加固 Electron；
3. 建立 Worker 协议、生命周期和资源限制；
4. 接入随包 Pyodide，并让现有课程通过统一运行接口调用；
5. 删除旧动态模拟器并启用严格 CSP；
6. 建立存档仓库、完整性校验和恢复记录；
7. 执行攻击测试、生产构建和桌面运行验收。

每一步先写会失败的测试，确认测试能够发现缺陷后，再做最小实现。不得在同一提交中混入无关 UI 或课程内容重写。
