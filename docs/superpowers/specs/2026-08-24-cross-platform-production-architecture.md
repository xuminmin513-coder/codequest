# XM²code 跨平台生产架构设计

日期：2026-08-24
状态：用户已批准，进入分阶段实施

## 1. 目标

XM²code 要从当前可运行的 React/Electron 教学原型，演进为可以长期维护并发布到 macOS、Windows、Linux、iOS、Android、HarmonyOS 手机/平板/电脑的编程教育产品。

架构必须同时保证：零基础课程体验一致、玩家代码不能触达宿主设备、未登录也能离线学习、登录后才同步、课程更新不破坏进度、各平台可以独立分阶段发布和回滚。

## 2. 已确认的产品约束

- 品牌统一使用 `XM²code`，标记使用 `XM²`。
- 中文简体和英文首发；语言资源从第一天与业务代码分离。
- 玩家第一次进入只有一个默认存档槽，确有需要时通过“添加存档槽”增加。
- 未登录玩家可以完整离线学习；主动登录后才开启跨设备同步、云端备份和项目同步。
- 所有正式挑战从空白编辑器开始，不提供本题预填答案。
- 每关经过演示、执行轨迹、微检查、独立完整编码、变式或复习。
- 代码解释只显示解释正文，不显示“大白话：”前缀。
- 通关后保留礼花效果。
- 复习间隔为 1、2、4、7、15、30 天；答错当天补救并重置间隔。
- HarmonyOS 范围包括手机、平板、折叠屏和华为 HarmonyOS 电脑；运行 Windows 的华为电脑使用 Windows 版。

## 3. 总体架构

### 3.1 共享业务核心

React、课程模型、判题协议、掌握度、复习、存档领域模型、国际化键和设计令牌保持共享。平台外壳只能通过固定能力接口访问本地存储、账号、更新、系统信息和文件导入导出，业务组件不得直接依赖 Electron、Capacitor 或 HarmonyOS API。

建议最终目录边界：

```text
apps/
  desktop/                 Electron 主进程与桌面打包
  mobile/                  Capacitor iOS/Android 工程
  harmony/                 ArkUI/ArkWeb 与 HarmonyOS 原生桥接
  web/                     React/Vite 共享应用入口
packages/
  course-schema/           课程结构、验证与内容版本
  learning-core/           判题、掌握度与复习
  local-data/              存档领域模型、迁移与恢复
  platform-contract/       平台能力接口
  design-system/           设计令牌与共享组件
  i18n/                    语言资源与布局规则
services/
  api/                     账号、同步、课程清单、AI 代理
  runner/                  隔离云端代码运行调度
```

迁移采用渐进方式完成，当前 `src/` 不做一次性大搬家。每建立一个稳定包边界，再迁移对应代码，避免与课程重写同时进行大规模目录调整。

### 3.2 平台外壳

| 平台 | 外壳 | 首发架构 |
|---|---|---|
| macOS | Electron | arm64 与 x64 构建，签名与公证 |
| Windows | Electron | x64 首发，MSIX；ARM64 后续 |
| Linux | Electron | x64 首发，AppImage 与 deb |
| iOS | Capacitor | WebKit，App Store 分发 |
| Android | Capacitor | Android WebView，AAB 分发 |
| HarmonyOS | ArkUI + ArkWeb | 同一 HarmonyOS 工程，多设备适配 |

HarmonyOS 电脑不是把手机版按比例放大。必须验证自由窗口、分屏、折叠形态、键盘快捷键、鼠标/触控板、触摸等价操作和窗口变化时的任务连续性。

## 4. Python 执行架构

### 4.1 离线基础课程

所有平台统一使用固定版本的 Pyodide/WebAssembly，通过独立 Worker 执行。每次运行使用临时命名空间和虚拟文件系统；应用不提供宿主文件、真实网络、系统命令、Node 或原生桥接能力。

运行限制包括：代码长度、输入长度、时间、输出、虚拟文件数量和大小。停止、超时或崩溃后销毁 Worker。移动端只随包交付核心运行时与课程必要资源，不打包完整科学计算发行包。

### 4.2 高级课程

普通 Python、基础文件和 SQLite 继续在本地 Worker 中运行。真实后端、数据库服务、网络、第三方原生扩展和大型数据包进入云端一次性容器。线程、Socket、PySpark 和图表在云端运行器可用前使用明确标注的教学实验，不伪装为完整真实环境。

云端运行器与核心业务服务物理隔离：默认无外网、只读基础镜像、时间/内存/CPU/磁盘/输出配额、一次性工作目录、用后销毁。运行器不能连接用户数据库，只能通过队列领取经过校验的任务并回传固定结果。

## 5. 本地数据与同步

### 5.1 本地优先

本地存档是权威的离线数据源。UI 通过 `PlayerSaveRepository` 访问数据，不直接读写 `localStorage`。第一阶段允许 `localStorage` 作为物理介质，但领域数据必须有固定结构、完整性校验、迁移和恢复记录；后续桌面和移动端替换为本地数据库时不改业务 UI。

存档包包含：

- `schemaVersion`、`saveId`、`createdAt`、`updatedAt`；
- `deviceId`、课程版本、关卡进度、草稿、复习、成就和设置；
- 最近三份有效恢复记录；
- 对规范化数据计算的完整性校验值。

默认创建一个存档。新增存档必须由玩家主动点击。删除、覆盖、导入和恢复都需要明确目标，不允许通配或批量隐式操作。

### 5.2 登录后同步

未登录不创建云端身份，也不上传代码、学习记录或设备信息。登录后，客户端创建同步会话并上传本地变更日志。

进度和掌握度按知识点合并；设置使用最后修改时间；代码草稿发生双向修改时保留两个版本并让玩家选择，绝不静默覆盖。服务端使用幂等操作 ID，客户端断网重试不会重复写入。

## 6. 云端业务边界

初期后端采用 TypeScript 模块化单体，避免过早拆分微服务。模块包括账号、同步、课程内容清单、AI 解释代理、作品元数据和运营配置。代码运行器单独部署，因为其安全边界、资源模型和扩容方式不同。

基础设施使用托管 PostgreSQL、对象存储和 CDN。开发、测试、预发布、生产环境完全分离。生产数据库不与日常测试共用，备份保存在独立存储并定期进行恢复演练。

## 7. AI 代码解释

课程内固定示例优先使用人工审核、可离线显示的解释。玩家自写代码的动态解释经 XM²code 服务端代理；客户端不保存模型供应商密钥，也不直接请求模型平台。

每次上传前向玩家说明会发送的代码范围。后端负责脱敏、未成年人隐私规则、限额、成本预算、模型切换和安全审计。AI 只提供解释、定位和下一步行动，不能把本题完整答案写入编辑器。

## 8. 版本与兼容性

系统分别管理：

1. 客户端版本，如 `2.3.0`；
2. 课程内容版本，如 `2026.08.2`；
3. 云端 API 版本，如 `/v1`；
4. 运行器镜像版本，以不可变摘要固定；
5. 本地数据 `schemaVersion`。

API 至少兼容当前和前两个已发布客户端版本。课程升级不复用已改变含义的关卡版本；重大修改创建新内容版本并迁移掌握记录。数据库迁移使用扩展、切换、清理三阶段，旧客户端仍在使用时不得提前删除字段。

## 9. 发布和运维

发布链路：提交 → 单元/课程/安全测试 → 六平台构建 → 测试环境 → 内部测试 → 商店或更新渠道分阶段发布 → 指标观察 → 全量。

- macOS、Windows 构建签名；macOS 额外公证。
- Mac App Store 构建只使用商店更新；直接分发构建使用签名更新源。
- Windows Store 使用 MSIX 渐进发布。
- Linux 通过所选发行包或软件仓库更新，不依赖 Electron 内置更新器。
- iOS、Android、HarmonyOS 使用各自商店的测试轨道和分阶段发布。
- 每次发布保存构建产物、源提交、依赖锁、课程清单和运行器摘要的对应关系。

监控至少包括崩溃率、启动失败、同步失败、冲突率、代码运行失败、队列等待时间、课程退出率、AI 请求失败和成本。日志默认不记录完整玩家代码、输入、令牌或个人信息。

## 10. 实施阶段与验收门槛

### 阶段 0：本地执行安全

已完成：删除系统 Python 和动态 JavaScript 模拟器，移除客户端 DeepSeek 密钥，建立 Pyodide Worker、Electron 网络/权限边界和安全 E2E。

### 阶段 1：版本化本地存档

建立存档仓库、默认单槽、按需新增、三份恢复点、完整性校验、旧数据迁移、导入导出和 UI 集成。所有迁移失败都必须保持旧数据可恢复。

### 阶段 2：平台能力与外壳

建立统一平台合同；迁移 Electron；创建 Capacitor iOS/Android 工程；创建 HarmonyOS ArkUI/ArkWeb 工程；在真机或官方模拟器验证运行器、存档、编辑器和响应式布局。

### 阶段 3：云端业务与同步

建立 API、托管数据库模型、登录后同步、冲突处理、AI 代理、审计与限额。未登录模式必须在服务完全不可用时继续学习。

### 阶段 4：云端运行器

建立任务队列、一次性容器、资源配额、默认断网、镜像签名、审计与滥用防护；高级课程按清单逐项迁移。

### 阶段 5：发行与运维

建立六平台 CI、签名、公证、商店元数据、分阶段发布、监控、备份恢复、灾难演练和安全紧急更新通道。

## 11. 不采用的方案

- 不继续直接执行系统 Python。
- 不在客户端保存第三方模型 API Key。
- 不用一个服务器管理面板承担不受信玩家代码的生产运行。
- 不把全部业务过早拆成微服务或直接引入 Kubernetes。
- 不用一次性目录大搬家代替渐进式架构迁移。
- 不让课程内容更新直接覆盖玩家已完成记录或草稿。
